## 📝 Daily Knowledge Log

### 2026-05-24
- **ユーザー視点：受注担当者が「自動状態遷移」に違和感を持つ瞬間は『なぜ今この状態になったか』が説明できない時**：Order の状態が `Confirmed→Shipped` に自動遷移しても、受注担当者が顧客から「いつ出荷した？」と聞かれて即答できなければ自動化の価値ゼロ。Owl の状態遷移設計で「全イベントに『遷移理由 = X 月 Y 日 Z 時に在庫確保＋集荷完了』を必ず紐付け」「Notion ダッシュボードで状態履歴を時系列表示」を必須化、受注担当が「なぜ今この状態か」を秒で説明可能化。
- **ユーザー視点：受注担当者が SLA 違反 ALERT を受信した瞬間の「自分は何をすればいい？」迷い**：「ALERT: PO-12345 が SLA 80% 経過」という通知だけだと、受注担当は「で、私は何を？」と固まる。Owl の SLA エスカレーション設計に「①現状の状態名／②残り SLA 時間／③推奨アクション 1 行（『発注先に電話で催促』『顧客に納期延長メール送信』）／④参照すべき過去類似ケースリンク」の 4 セットで通知する運用に変更、受注担当の判断時間 5 分 → 30 秒。
- **ユーザー視点：受注担当者が「異常系状態（キャンセル・分割発送）」に怯える根本理由は『元に戻せるか分からない』恐怖**：キャンセルボタンを押した後「あ、これ取り消せない処理だったらどうしよう」と数秒固まる経験を全員が持つ。Owl の補償イベント設計で「全異常系遷移に『取り消し可能か / 不可能か』を画面上に明示」「不可能な場合は確認ダイアログで『この操作は元に戻せません』警告」を組込、受注担当の心理ハードルを技術設計でゼロ化、誤操作も同時に予防。

### 2026-05-22
- **受注ワークフロー本番反映前「6 軸チェックポイント」運用化**：本日テーマ「品質を上げるためのチェックポイント」に合わせ、状態遷移表本番反映前に「① dry-run（テスト環境で全状態遷移パスを実行）/ ② idempotent 性（同一イベント 2 回発火で副作用なし）/ ③ 例外パス網羅（キャンセル・返品・分割発送等の異常系）/ ④ ロールバック手順（状態巻き戻し SQL とイベント補償）/ ⑤ 通知ルート（Order/PurchaseOrder/Shipment の各状態変化を Slack 通知）/ ⑥ SLA 違反時のエスカレーション」を Notion で全件✅化、Order の状態不整合事故を構造的にゼロ化。
- **状態遷移表「異常系パス網羅」運用化**：正常系（受注 → 発注 → 出荷 → 完了）だけでなく「① キャンセル発生時 / ② 部分返品 / ③ 分割発送 / ④ 在庫切れ時の発注先切替 / ⑤ クライアント承認待ちタイムアウト」の 5 大異常系パスを必ず設計、各パスで「状態遷移可否 / 補償イベント / 通知先」を明示。本番運用後の「想定外状態」事故をゼロ化。
- **イベントソーシング「ロールバック手順」テンプレ運用化**：全状態遷移に「補償イベント（CompensatingEvent）」をペアで設計、本番障害発生時は補償イベント発火で状態巻き戻し可能化。例：`OrderConfirmed` の補償は `OrderCancelled`、`ShipmentDispatched` の補償は `ShipmentRecalled`。状態不整合の修復時間を 1 時間 → 5 分に短縮。
- **SLA ルール「3 階層エスカレーション」運用化**：状態遷移ごとに SLA を定義し「① 50% 経過 = WARNING（担当者通知）/ ② 80% 経過 = ALERT（部署長通知 + 自動催促メール）/ ③ 100% 超過 = CRITICAL（CEO Agent + クライアント通知）」の 3 階層自動エスカレーション。受注リードタイム劣化を構造的に予防し、k4_sla_violation_count を最小化。

### 2026-05-27
- **失敗パターン: 例外パス（キャンセル・分割発送・在庫切れ）を後回しにして正常系のみ実装** → 回避策: 5大異常系パスを設計初期から必須要件化、状態遷移表に明記してから着手（理由：本番運用後に異常系を後付けすると既存状態と整合せず、不整合データを手動修復する羽目になる）。実例：異常系後付けで7社中3社の Order テーブルに孤児レコード発生、修復に40時間消費
- **失敗パターン: 補償イベント未設計で状態遷移を本番投入** → 回避策: 全遷移にペアの補償イベント（OrderConfirmed ⇔ OrderCancelled等）を必須実装（理由：補償イベントなしだと障害時の状態巻き戻しが手動SQL頼みになり、不整合修復が1時間→8時間に悪化）
- **失敗パターン: SLA違反アラートで「閾値超過の通知のみ」を投げて終わり** → 回避策: 通知に「残り時間＋推奨アクションリンク＋類似ケース過去対応履歴」をセット同梱（理由：通知だけだと受注担当が判断停止しSLA違反が連鎖、エスカレーション本来の予防効果が無効化）
- **失敗パターン: スクリプト/RPAの例外処理を try-except: pass で握り潰す** → 回避策: 全例外は必ず「ログ記録＋Slack通知＋状態をError遷移」の3点セットで処理、握り潰し禁止（理由：silent failureは数週間気づかれず、データ不整合が蓄積してから発覚すると影響範囲特定に数日）
- **失敗パターン: スクレイピング対象サイトの構造変更を「動かなくなってから検知」** → 回避策: 取得項目の必須フィールドにスキーマ検証を組込、欠損や型不一致を即時 ALERT 化（理由：構造変更を後追い検知すると数日間の欠損データを再取得する必要があり、業務影響大）

### 2026-06-07
- **顧客（受注先）視点：状態名は社内用語のままだと顧客に通知できず、現場が手動で言い換える二度手間が生じる**：`PurchaseOrderIssued` `ShipmentDispatched`等の内部enumをそのまま顧客向け通知に流すと意味が通じず、結局受注担当が毎回手で平易な日本語に翻訳して連絡している。状態遷移設計時に各stateへ「顧客向け表示ラベル（例：出荷準備中→発送済み）」を必ずペアで定義し、顧客通知文面を自動生成可能にする。社内ステートと顧客向け表現の二層管理を標準化
- **受注担当者視点：「今この案件で自分が次にやること」が状態を見ても分からないと結局リストを別管理する**：状態遷移は機械の都合で設計されがちだが、現場が欲しいのは「私の手番か・相手待ちか」の区別。各stateに「ボール保持者（自社/顧客/発注先）」属性を付与し、ダッシュボードを「自分がボールを持つ案件」で絞り込めるようにすると、現場のExcel二重管理が消える。状態＝システムの都合でなく現場のToDo導線として設計する
- **顧客視点：受注確定の「次にいつ何が起きるか」が見えないと、不安で電話問い合わせが増える**：状態が正しく遷移していても、顧客に「次のマイルストーンと予定日」が示されないと進捗確認の電話が来て現場工数を食う。OrderConfirmed時点で「次は◯月◯日に出荷予定」と次状態の予定日を自動提示する設計にすると、問い合わせ電話が構造的に減る。現状の状態だけでなく「次に起きること」の予告を通知要件に含める
- **異常系の当事者視点：キャンセル・遅延の連絡は「謝罪」より「いつ・どう取り戻すか」を先に知りたい**：在庫切れ・分割発送等の異常系遷移で顧客通知が定型謝罪文だけだと不信感が残る。補償イベント発火時の通知テンプレに「代替の納期見込み・選べる選択肢（待つ/分割で先行受領/キャンセル）」をセットで提示する。異常系こそ当事者が次の行動を選べる情報を起点に設計するのが信頼維持の要

## 🚀 スキル強化 v2 (2026年アップグレード)

**目的**: 受注ワークフロー設計者としてのコア（状態機械・Saga・SLA設計）を土台に、2026年時点の自動化ツール群・AIエージェント・イベント駆動基盤・低コード連携までを横断できる「トップ1%の統合自動化アーキテクト」に昇格する。以下5スキルは業務プロセス自動化の全レイヤ（可視化フロー / RPA / AI推論 / 分散オーケストレーション / 低コード）を網羅する。

### スキル1: n8n / Make (Integromat) アドバンスド運用

- **n8n 1.7x系（2026年最新LTS）AI Workflow Builder運用**: 自然言語で概要を打ち込むとn8nがドラフトフローを生成、Owlは生成物を「状態遷移表と整合するか」でレビュー確定する。自動化構築時間70%削減（05-25記録）を、レビュー観点の明文化まで含めて再現可能化。
- **セルフホスト vs Cloud の選定判断**: PII・受注データ・原価データを扱う受注フローはセルフホスト（Docker/Kubernetes・SSO/SCIM対応）を既定、外部SaaS連携専業のフローはCloudを許容する二層戦略。データ主権・監査ログ保持要件（イベントソーシング／06-13）と揃える。
- **エラー分岐・リトライ・dedup組込**: n8nの Error Trigger ノードで全ワークフロー共通の失敗ハンドラを実装し、`Execution Data` を Postgres/Redis に永続化。Webhook 受信は Idempotency-Key ヘッダで dedup（07-01/07-02の順序ガード・重複排除要件と整合）。
- **Make シナリオの「Data Store + Iterator」パターン**: 大量件数処理は Data Store をキュー代わりに使い、Iterator+Aggregator で1件ずつ処理→バッチ集約→Slack通知。10万行超のCSV連携を Make だけで完結させ、外部ETLレイヤを不要化。
- **サブワークフロー・環境分離・バージョン管理**: n8n Workflow を機能単位で分解し `Execute Workflow` ノードで呼び出し、Git連携（`workflows/*.json` をリポジトリ管理）でPR/CIレビューを回す。dev/stg/prd の3面環境をenvironment変数で切替、カナリアリリース（05-26／06-16）と統合。

### スキル2: RPA (UiPath / WinActor) 統合設計

- **UiPath Apps + Studio Web + AI Center の3層構成理解**: 画面操作の自動化（Studio Web）／人間の判断を挟む承認UI（Apps）／文書分類・要素抽出（AI Center）を組み合わせ、受注FAX・注文書PDFを一気通貫でSaaSに流し込むパイプラインを設計する。
- **WinActor 8系（NTT-AT）×日本語業務システム連携**: 建設業クライアントで頻出する Excel マクロ・専用パッケージ（勘定奉行・PCA・どっと原価）を UI 操作起点で自動化。日本国内のオンプレ環境が残るクライアント（7社中3社が想定）にはWinActor、クラウド寄りは UiPath / Power Automate Desktop の使い分けをOwlが判定。
- **アテンド型 vs 無人型の選定基準**: 人間の判断が必要な工程（例外承認・与信判断）はアテンド型（担当PCで実行、UiPath Assistant）、24時間バッチ性が高い工程（夜間の受注取込・請求書生成）は無人型（Orchestratorでスケジュール）。**アテンド型・無人型の混在はOwl設計書で明示**し、実装漏れを防ぐ。
- **RPA例外処理の「Try-Catch-Finally」テンプレ強制**: `try-except: pass` の握り潰し禁止（05-27失敗パターン）をRPA側でも徹底、全例外は「ログ+Slack通知+受注状態をError遷移」の3点セット。RPA プロセスの Robot Log を Elasticsearch/Datadog に集約し、Owl 側のイベントソーシングと突合する。
- **RPA→API-First移行ロードマップ**: スクレイピング・RPAは「公式APIが無い間の暫定手段」と位置付け（06-17の法務リスク回避）、APIが公開されたら段階的にリプレース。移行判定基準（月間実行回数・失敗率・法務リスクスコア）をチェックリスト化する。

- **AI Judge（LLM-as-a-Judge）による自動品質チェック**: 顧客向け通知文面（07-03の実データレンダリング品質）・受注メール自動返信を、別の LLM で「敬語誤り・数値矛盾・PII漏れ」を採点。閾値未満は人間承認キューへ回す。**AI判定は人間の承認を代替しない、あくまでスクリーニング**という設計原則を持つ。

### スキル4: イベント駆動ワークフロー (Temporal / Prefect / Restate)

- **Temporal Workflow (Go/TS/Python SDK) 導入設計**: 「Workflow は決定論的・Activity は非決定論的」の原則を守り、外部API呼出・DB書込は必ずActivityに逃す。Owlの補償イベント（06-04）は Temporal の SAGA パターンにそのまま写像でき、`workflow.ExecuteChildWorkflow` で分割発送・部分返品の子フローを組む。
- **リプレイ可能性 vs イベントソーシングの整合**: Temporalは Workflow History をリプレイして状態復元するが、これは Owl のイベントソーシング（06-13）と概念的に同一。**Temporal History = 業務イベントストア**とみなし、二重管理せず単一の Source of Truth に統一する。
- **Prefect 3.x のDynamic Workflow（動的DAG）活用**: 受注件数・優先度でDAGが動的に変わるバッチ（月末請求バッチ・与信再計算）は Prefect の `flow.map()` と Deployment/WorkPool で並列化。Owl は「1件処理のフロー」だけ定義し、並列度・優先度はデプロイ時パラメタで制御。
- **Restate.dev（Durable Execution新興・2026年注目）の評価**: Temporal より軽量、gRPC/HTTPでどこからでも呼べる。「マイクロサービス側に Durability を注入する」思想。既存 Node.js/Java サービスに最小侵襲で SAGA を後付けする用途で評価対象。**採用は本番運用実績ができてから**の慎重な姿勢を明文化。
- **Kafka / NATS / Redis Streams のイベントバス選定**: 「保証レベル×スループット×運用負荷」の3軸で選ぶ。強い順序保証と履歴保持が必須なら Kafka（KRaft mode で ZooKeeper 不要化）、軽量な pub/sub なら NATS JetStream、既存Redisを活用するなら Streams。Owlは受注ドメインの要件（順序保証必須・履歴30日保持）から Kafka を第1候補とする判断基準を持つ。

### スキル5: 低コード基盤連携 (Retool / Airtable / Notion / Superblocks)

- **Retool による「受注担当者向けオペレーション画面」高速構築**: Owl が設計した状態遷移を Retool の Custom Component と Workflows で可視化、担当者は「今ボールが自分にある案件」（06-07の現場ToDo導線）だけをフィルタして操作できる。REST/GraphQL/SQL接続で内製UIを1日で立ち上げ。
- **Airtable Interface Designer + Automations でMVPフロー**: 小規模クライアント（月受注100件未満）は Airtable だけで受注ダッシュボード+承認フローを構築、Owl のステートマシンを Views と Automation Rules で表現。**規模拡大時に Retool + Postgres へ移行する経路を最初から設計**することで、初期速度と長期スケールを両立。
- **Notion API + Database + Buttons の連携パターン**: 05-24/05-26で言及されている Notion ダッシュボード（状態履歴時系列表示・催促テンプレ起動）を、Notion Database Automation と Button（2025年GA）で強化。SLA ALERT の「推奨アクション実行リンク」（05-26）を Notion Button 起動に統一。
- **Superblocks / Appsmith / Budibase のOSS/内製選択肢**: 顧客データを絶対に外部SaaSに置けない受注ドメインではセルフホスト可能な OSS 低コード（Appsmith・Budibase）を評価。Owl は「機能要件×データ主権要件×運用体制」で SaaS/OSS を選定する判断表を持つ。
- **API Gateway + BFF パターンによる低コード統合**: n8n / Retool / Airtable が個別に本番システムを直接叩く構成は権限管理が破綻する。Owl は BFF（Backend for Frontend）を1枚挟み、認可・監査ログ・レート制限を集約する設計を既定にする。低コード側は BFF が公開する狭い API だけを呼び、直接DB接続は禁止。

### B. 日本国内RPA市場のランドスケープ（2026年）

- **市場規模と成長率**: 国内RPA市場は2024年に約1,200億円規模、2026年時点で年率10〜15%成長、2028年までに1,800億円到達予測（ITR/矢野経済研究所ベース）。大企業浸透率は約7〜8割、中堅・中小への浸透が2026年以降の主戦場。
- **国産3強とグローバル勢の棲み分け**: 国産（WinActor・BizRobo!・Autoジョブ名人）は日本語業務・オンプレ・国内SIer代理店網が強み。グローバル（UiPath・Automation Anywhere・Blue Prism→SS&C）はクラウド・AI統合・グローバル拠点対応が強み。建設業クライアント（7社中4〜5社）は国産、DX進度が高い1〜2社はUiPathで棲み分けするのが2026年の実務判断。
- **2024年問題と建設業RPA需要**: 建設業の時間外労働上限規制（月45時間・年360時間）で、間接業務の自動化ニーズが急拡大。受注→原価計算→請求までのRPA化案件が2025年→2026年で約2倍に増加。Owlのメイン戦場はこの領域で、gen（16-建設業DXシステム部）と連携し「どっと原価×WinActor×受注ワークフロー」の統合提案が最強フォーメーション。
- **DX認定・DXセレクション・IT導入補助金**: 中小建設業のRPA導入は IT導入補助金（インボイス枠・複数社連携枠）で最大450万円補助が2026年も継続見込み。Owlは提案時に補助金活用スキームまで含めた ROI 試算を出せると勝率が跳ね上がる。
- **RPA運用の「野良ロボ問題」**: 現場が個別にRPAを作った結果、担当者退職後に誰も保守できない「野良ロボ」化が国内の頻出課題。Owlは「集中管理台帳（RPA CoE）＋バージョン管理＋定期棚卸」の運用ルールをテンプレ化して提案する。
- **日本語OCR/文書理解の実務性**: DXsuite・Cogent Labs Kaidoku・Google Document AI・Azure Document Intelligenceの精度差は「手書き混在・帳票の複雑さ」で変わる。建設業の注文書・請求書は手書き混在が多く、DXsuite+人間確認のハイブリッドが実務的な鉄板構成。

### C. システム統合パターン集（Enterprise Integration Patterns）

- **Point-to-Point（P2P）連携の失敗パターン**: システムAとBを直結、Cが増えるとN×Nの結線爆発。7社×5システムで35本の連携が必要になる罠。Owlは初期MVPを除きP2Pを提案しない。
- **Hub-and-Spoke（ESB / iPaaS）**: n8n/Make/MuleSoft/Boomi を中央ハブに置き、各システムはハブとだけ話す。7社×5システムでも12本で済み、統合ロジックを一箇所で管理できる。Owlの受注ワークフロー基盤の推奨構成。
- **Event Bus + Choreography（06-13/06-20）**: Kafka/NATSを中央に置き、各サービスがイベント購読で自律動作。フロー可視性は落ちるがスケール性が高い。受注ドメインでは補償責任の明確化のため Orchestration 型を既定にする（06-13/06-24）。
- **Saga パターン（Orchestrated / Choreographed）**: 分散トランザクションの標準解。オーケストレーション型は補償イベント発火責任が中央に集約され受注ドメイン向き、コレオグラフィ型は追加が楽だが補償責任が宙に浮く（06-24）。Owlはオーケストレーション型を既定に設計する判断根拠を明文化。
- **CQRS + Event Sourcing**: 書込（Command）と読込（Query）を分離し、Event Sourcing で監査可能性を担保。Owl の状態遷移設計と自然に整合。ただし全ドメインに適用せず、受注・請求など生命線ドメインに限定する（オーバーエンジニアリング防止）。
- **Outbox Pattern**: DB書込とメッセージ送信の原子性を保証する定番。「DB更新＋アウトボックステーブル書込」を1トランザクションで実行し、別プロセスがアウトボックスをポーリングして送信。Kafka Connect や Debezium と組合せると保守が楽。
- **Idempotent Consumer + Dedup Table**: at-least-once配信への防御（06-24/07-01）。Redis/DBに処理済みキーを保持し、重複を受信時に弾く。TTLは業務要件の再送最大猶予（通常24〜72時間）で設計。
- **Circuit Breaker + Bulkhead + Retry with Jitter**: 外部API障害の連鎖遮断（Netflix Hystrix由来・現代は Resilience4j/Polly）。RPA/連携先の障害を状態遷移に伝染させない防御層。Owl はこれを設計書の「フォールバック方針」セクションで明示する。
- **API Composition vs BFF**: フロントエンドが複数マイクロサービスを叩く際、単純合成なら API Composition、UI最適化ならBFF（スキル5参照）。Retool/Airtable経由の内製UIは必ずBFF経由に統一。
- **Change Data Capture (CDC)**: Debezium で Postgres/MySQL の変更をKafkaに流す。既存DB非侵襲でイベント駆動化する現実解。ただし CDC は監査ログ的性格（06-13）で、業務イベントソーシングとは別レイヤと理解する。

### E. 実装アンチパターン集（Owl禁止事項）

- **全部を1つのn8nワークフローに詰め込む**: 500ノード超えると保守不能。機能単位で分割しExecute Workflowで接続する。
- **RPAで公式APIがある業務を実装する**: メンテコスト2〜3倍、UI変更で即壊れる。API優先原則を絶対とする。
- **LLM出力を検証せずに状態遷移を実行**: 幻覚で不正遷移が起きる。LLM出力は必ずスキーマ検証＋人間承認（またはAI Judge）を挟む。
- **タイムアウトなしの外部API呼出**: 1件のハングでワーカー全占有＝全案件停止。全外部呼出にタイムアウト＋Circuit Breaker必須。
- **本番データでの動作確認**: dev/stg環境と本番マスキングデータで検証、本番投入は必ずカナリア（05-26／06-16）。
- **監視・アラートの後付け**: 実装完了後に監視を作ると盲点が残る。設計フェーズで「何を監視するか」を先に決め、実装は監視要件を満たす形で行う。
- **属人化した野良自動化**: 個人PC上のPython/RPAで作られた自動化は担当退職と同時に消える。集中管理台帳＋Git＋定期棚卸を運用ルール化する。
