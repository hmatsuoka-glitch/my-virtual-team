## 📝 Daily Knowledge Log

### 2026-05-24
- **ユーザー視点：受注担当者が「自動状態遷移」に違和感を持つ瞬間は『なぜ今この状態になったか』が説明できない時**：Order の状態が `Confirmed→Shipped` に自動遷移しても、受注担当者が顧客から「いつ出荷した？」と聞かれて即答できなければ自動化の価値ゼロ。Owl の状態遷移設計で「全イベントに『遷移理由 = X 月 Y 日 Z 時に在庫確保＋集荷完了』を必ず紐付け」「Notion ダッシュボードで状態履歴を時系列表示」を必須化、受注担当が「なぜ今この状態か」を秒で説明可能化。
- **ユーザー視点：受注担当者が SLA 違反 ALERT を受信した瞬間の「自分は何をすればいい？」迷い**：「ALERT: PO-12345 が SLA 80% 経過」という通知だけだと、受注担当は「で、私は何を？」と固まる。Owl の SLA エスカレーション設計に「①現状の状態名／②残り SLA 時間／③推奨アクション 1 行（『発注先に電話で催促』『顧客に納期延長メール送信』）／④参照すべき過去類似ケースリンク」の 4 セットで通知する運用に変更、受注担当の判断時間 5 分 → 30 秒。
- **ユーザー視点：受注担当者が「異常系状態（キャンセル・分割発送）」に怯える根本理由は『元に戻せるか分からない』恐怖**：キャンセルボタンを押した後「あ、これ取り消せない処理だったらどうしよう」と数秒固まる経験を全員が持つ。Owl の補償イベント設計で「全異常系遷移に『取り消し可能か / 不可能か』を画面上に明示」「不可能な場合は確認ダイアログで『この操作は元に戻せません』警告」を組込、受注担当の心理ハードルを技術設計でゼロ化、誤操作も同時に予防。

### 2026-05-22
- **受注ワークフロー本番反映前「6 軸チェックポイント」運用化**：本日テーマ「品質を上げるためのチェックポイント」に合わせ、状態遷移表本番反映前に「① dry-run（テスト環境で全状態遷移パスを実行）/ ② idempotent 性（同一イベント 2 回発火で副作用なし）/ ③ 例外パス網羅（キャンセル・返品・分割発送等の異常系）/ ④ ロールバック手順（状態巻き戻し SQL とイベント補償）/ ⑤ 通知ルート（Order/PurchaseOrder/Shipment の各状態変化を Slack 通知）/ ⑥ SLA 違反時のエスカレーション」を Notion で全件✅化、Order の状態不整合事故を構造的にゼロ化。
- **状態遷移表「異常系パス網羅」運用化**：正常系（受注 → 発注 → 出荷 → 完了）だけでなく「① キャンセル発生時 / ② 部分返品 / ③ 分割発送 / ④ 在庫切れ時の発注先切替 / ⑤ クライアント承認待ちタイムアウト」の 5 大異常系パスを必ず設計、各パスで「状態遷移可否 / 補償イベント / 通知先」を明示。本番運用後の「想定外状態」事故をゼロ化。
- **イベントソーシング「ロールバック手順」テンプレ運用化**：全状態遷移に「補償イベント（CompensatingEvent）」をペアで設計、本番障害発生時は補償イベント発火で状態巻き戻し可能化。例：`OrderConfirmed` の補償は `OrderCancelled`、`ShipmentDispatched` の補償は `ShipmentRecalled`。状態不整合の修復時間を 1 時間 → 5 分に短縮。
- **SLA ルール「3 階層エスカレーション」運用化**：状態遷移ごとに SLA を定義し「① 50% 経過 = WARNING（担当者通知）/ ② 80% 経過 = ALERT（部署長通知 + 自動催促メール）/ ③ 100% 超過 = CRITICAL（CEO Agent + クライアント通知）」の 3 階層自動エスカレーション。受注リードタイム劣化を構造的に予防し、k4_sla_violation_count を最小化。

### 2026-05-27
- **失敗パターン: 例外パス（キャンセル・分割発送・在庫切れ）を後回しにして正常系のみ実装** → 回避策: 5大異常系パスを設計初期から必須要件化、状態遷移表に明記してから着手（理由：本番運用後に異常系を後付けすると既存状態と整合せず、不整合データを手動修復する羽目になる）。実例：異常系後付けで7社中3社の Order テーブルに孤児レコード発生、修復に40時間消費
- **失敗パターン: 補償イベント未設計で状態遷移を本番投入** → 回避策: 全遷移にペアの補償イベント（OrderConfirmed ⇔ OrderCancelled等）を必須実装（理由：補償イベントなしだと障害時の状態巻き戻しが手動SQL頼みになり、不整合修復が1時間→8時間に悪化）
- **失敗パターン: SLA違反アラートで「閾値超過の通知のみ」を投げて終わり** → 回避策: 通知に「残り時間＋推奨アクションリンク＋類似ケース過去対応履歴」をセット同梱（理由：通知だけだと受注担当が判断停止しSLA違反が連鎖、エスカレーション本来の予防効果が無効化）
- **失敗パターン: スクリプト/RPAの例外処理を try-except: pass で握り潰す** → 回避策: 全例外は必ず「ログ記録＋Slack通知＋状態をError遷移」の3点セットで処理、握り潰し禁止（理由：silent failureは数週間気づかれず、データ不整合が蓄積してから発覚すると影響範囲特定に数日）
- **失敗パターン: スクレイピング対象サイトの構造変更を「動かなくなってから検知」** → 回避策: 取得項目の必須フィールドにスキーマ検証を組込、欠損や型不一致を即時 ALERT 化（理由：構造変更を後追い検知すると数日間の欠損データを再取得する必要があり、業務影響大）

### 2026-06-07
- **顧客（受注先）視点：状態名は社内用語のままだと顧客に通知できず、現場が手動で言い換える二度手間が生じる**：`PurchaseOrderIssued` `ShipmentDispatched`等の内部enumをそのまま顧客向け通知に流すと意味が通じず、結局受注担当が毎回手で平易な日本語に翻訳して連絡している。状態遷移設計時に各stateへ「顧客向け表示ラベル（例：出荷準備中→発送済み）」を必ずペアで定義し、顧客通知文面を自動生成可能にする。社内ステートと顧客向け表現の二層管理を標準化
- **受注担当者視点：「今この案件で自分が次にやること」が状態を見ても分からないと結局リストを別管理する**：状態遷移は機械の都合で設計されがちだが、現場が欲しいのは「私の手番か・相手待ちか」の区別。各stateに「ボール保持者（自社/顧客/発注先）」属性を付与し、ダッシュボードを「自分がボールを持つ案件」で絞り込めるようにすると、現場のExcel二重管理が消える。状態＝システムの都合でなく現場のToDo導線として設計する
- **顧客視点：受注確定の「次にいつ何が起きるか」が見えないと、不安で電話問い合わせが増える**：状態が正しく遷移していても、顧客に「次のマイルストーンと予定日」が示されないと進捗確認の電話が来て現場工数を食う。OrderConfirmed時点で「次は◯月◯日に出荷予定」と次状態の予定日を自動提示する設計にすると、問い合わせ電話が構造的に減る。現状の状態だけでなく「次に起きること」の予告を通知要件に含める
- **異常系の当事者視点：キャンセル・遅延の連絡は「謝罪」より「いつ・どう取り戻すか」を先に知りたい**：在庫切れ・分割発送等の異常系遷移で顧客通知が定型謝罪文だけだと不信感が残る。補償イベント発火時の通知テンプレに「代替の納期見込み・選べる選択肢（待つ/分割で先行受領/キャンセル）」をセットで提示する。異常系こそ当事者が次の行動を選べる情報を起点に設計するのが信頼維持の要

### 🔧 新規習得スキル

#### 1. 【自動化ROIスコアによる着手前GO/NO-GO判定】
**なぜ必要か**：既存Logは「作った後の品質」に全振りで、「そもそも作るべきか」の関所が無い。月10分しか削らない自動化でも保守は等しく発生し、7社分溜まると保守だけで人員1名分を食う。
**具体的手法**：依頼受領時に必ず ROI シートを起票し、①年間削減時間 ②構築工数 ③年間保守工数（＝構築工数×0.3を既定） ④失敗対応工数（＝月間実行回数×想定失敗率×15分）を積み、ペイバック月数を算出。nori 関所通過後・設計着手前に判定する。
**判断基準・数値ライン**：
- 人件費換算 **3,500円/時**（LET事務職想定）で統一
- **ペイバック 6ヶ月以内＝GO** ／ 6〜12ヶ月＝条件付GO（テンプレ流用が前提） ／ **12ヶ月超＝NO-GO**
- **月間削減 2時間未満は原則自動化しない**（保守が上回る）
- ただし「ミス1件の損害が10万円超」の統制目的は削減時間ゼロでもGO（リスク低減枠）
**実務テンプレート**：
```csv
# automation-roi.csv
id,依頼元,業務名,月間実行回数,1回手作業分,年間削減h,構築h,年間保守h(構築×0.3),想定失敗率,失敗対応h,初期費用円,年間削減円,payback_months,判定
AUT-014,ryota,月次レポート添付送付,28,12min,67.2,16,4.8,0.03,2.1,56000,235200,2.9,GO
```
`payback_months = (構築h×3500) ÷ ((年間削減h − 年間保守h − 失敗対応h) × 3500 ÷ 12)`
**期待効果**：低ROI案件の着手を入口で止め、保守対象を絞る。経営報告も 08-16 の金額換算テンプレと同じ単価で接続できる。

#### 2. 【自動化基盤の選定マトリクス（GAS / n8n / Zapier / Make / Temporal）】
**なぜ必要か**：07-27 で Temporal・n8n の動向は掴んだが「どれをいつ使うか」が未定義で、担当者の慣れで選ばれている。後から移行すると再実装コストが構築工数と同額かかる。
**具体的手法**：5軸（月間実行回数／状態保持期間／外部システム数／機密度／改修頻度）でスコアし、合計で基盤を機械決定する。
**判断基準・数値ライン**：
- **GAS**：Google Workspace 内で完結・月3,000実行以下・単発6分以内・機密度中まで。制約＝**実行6分/回・トリガー20個/ユーザー・スクリプト実行時間90分/日**。これを超えたら即 n8n 検討。
- **Zapier / Make**：外部SaaS 2〜4本を繋ぐだけ・月2,000タスク以下・非エンジニア運用。**月2,000タスク超で n8n セルフホストが月額で逆転**するのが分岐点。
- **n8n（セルフホスト）**：分岐/ループあり・月2,000タスク超・APIキーを自社管理したい場合。VPS 月5,000円前後を固定費として ROI シートの初期費用に計上。
- **Temporal 等 Durable Execution**：**状態保持が3日超**の長寿命プロセス（承認待ち・納品待ち）。SLAタイマー永続化（06-17）を自前実装しない代わりに運用コストを払う。
- 機密度「個人情報・原価・請求」を含むなら **SaaS中継禁止**、自社ホストか GAS（Workspace内）に限定。
**実務テンプレート**：
```yaml

change_frequency: low
decision: GAS          # 高機密→SaaS中継不可 / 6分内 / Workspace完結
reject_reason: {zapier: "原価データの外部SaaS通過は不可", n8n: "月320実行では固定費が回収不可"}
```
**期待効果**：選定を10分で終え、根拠を台帳に残す。移行の手戻り（構築工数の再発生）を構造的に防ぐ。

#### 3. 【リトライ標準ポリシー：指数バックオフ＋フルジッタ／DLQ／サーキットブレーカー】
**なぜ必要か**：06-20 で「冪等性と再実行安全は別物」と定義済みだが、**再実行安全側の具体値が未定義**。実装者ごとに「3回即時リトライ」など任意実装され、相手APIのレート制限を悪化させて障害を長引かせている。
**具体的手法**：全ジョブ共通の `retry_policy.yaml` を1本持ち、ジョブ側は名前で参照するだけにする。冪等キー（08-12）は送信アクション単位で必ず同梱。
**判断基準・数値ライン**：
- 初回待機 **1秒・倍率2・最大待機60秒・最大5試行**（合計約2分で打ち切り）
- **フルジッタ**必須：`wait = random(0, min(60, 1×2^n))`。同期再送によるサーバー側スパイクを回避
- **HTTP 429 / 503 は Retry-After ヘッダを最優先**（自前計算より常に優先）
- **4xx（429以外）はリトライ禁止**＝即DLQ。リトライしても永遠に通らない
- 5試行失敗で **DLQ（Dead Letter Queue）** へ退避。DLQ滞留 **10件超 or 24時間滞留で人へエスカレーション**
- **サーキットブレーカー**：連続失敗5回でOPEN（以後60秒は即失敗）→ハーフオープンで1件試行→成功でCLOSE
- **毒メッセージ（poison）**：同一イベントIDが3回DLQ入りしたら自動リラン対象から除外し要調査ラベル
**実務テンプレート**：
```yaml
# retry_policy.yaml
default:
  max_attempts: 5
  base_wait_sec: 1
  multiplier: 2
  max_wait_sec: 60
  jitter: full
  honor_retry_after: true
  no_retry_status: [400,401,403,404,409,422]
  dlq: dlq_default
  circuit_breaker: {failure_threshold: 5, open_sec: 60, half_open_probes: 1}
external_edi:   # 発注先EDI・Peppol（08-03記録）
  max_attempts: 8
  max_wait_sec: 300
  idempotency_key: "{source_id}:{message_id}:{issued_date}"  # 08-05の複合キー
```
**期待効果**：外部API起因の失敗を人手介入なしで吸収し、吸収できない失敗だけをDLQに集約。障害時の「どこまで再送されたか不明」を根絶。

#### 4. 【実行ログ監査基盤（run_log スキーマ・相関ID・マスキング・保持13ヶ月）】
**なぜ必要か**：06-13 のイベントソーシングは**業務イベント**の履歴で、**自動化ジョブ自体**の実行記録は対象外。「昨日の夜、転記は動いたのか」に即答できず、障害調査が実装者へのヒアリングから始まっている。
**具体的手法**：全ジョブが開始・終了時に共通スキーマで1行ずつ追記。業務イベントIDを `correlation_id` に持たせ、ジョブログ↔状態遷移ログを双方向に辿れるようにする。
**判断基準・数値ライン**：
- **保持13ヶ月**（前年同月比較が可能な最小期間）。以降は月次集計のみ残す
- **成功率SLO 99.5%**／**ログ欠損率 0.1%未満**（欠損＝startありendなしの率）
- ログへの **PII・原価・請求金額は書かない**（キー参照のみ）。やむを得ない場合は先頭2文字＋マスク
- 実行時間が **直近30日中央値の3倍**を超えたら遅延ALERT（失敗していなくても異常兆候）
- 週次で「連続成功日数」「DLQ件数」「平均実行時間」の3列サマリを自動投稿
**実務テンプレート**：
```sql
CREATE TABLE run_log (
  run_id          TEXT PRIMARY KEY,   -- ULID
  job_name        TEXT NOT NULL,
  trigger_type    TEXT,               -- schedule/webhook/manual
  actor           TEXT,               -- service account id（人名でなく主体ID）
  correlation_id  TEXT,               -- 業務イベントID（状態遷移ログと突合）
  started_at      TIMESTAMPTZ NOT NULL,
  ended_at        TIMESTAMPTZ,
  status          TEXT,               -- success/failed/retrying/dlq/skipped_dedup
  attempt         INT DEFAULT 1,
  input_digest    TEXT,               -- 入力のSHA256（中身は保存しない）
  error_class     TEXT,
  error_message   TEXT,               -- マスキング済み
  rows_affected   INT
);
```
**期待効果**：「動いたか／何件処理したか／なぜ止まったか」を人に聞かずに answer できる。監査・クライアント説明にもそのまま出せる。

#### 5. 【権限最小化とシークレット運用（サービスアカウント・OAuthスコープ・ローテ）】
**なぜ必要か**：07-03/08-12 の権限設計は**業務ロール**の話で、自動化が使う **API資格情報**は無管理。担当者個人のGoogleアカウントで動く GAS が残ると、退職・パスワード変更で全自動化が同時停止する。
**具体的手法**：全自動化を**サービスアカウント（機能アカウント）実行**へ寄せ、資格情報は台帳で棚卸しする。人アカウント実行は例外申請制。
**判断基準・数値ライン**：
- **個人アカウント実行は禁止**。例外は期限90日付きで台帳に理由を記録
- OAuth スコープは**読み取り優先**。`drive`（全体）でなく `drive.file`（自作成ファイルのみ）等、最小スコープを選択
- APIキー・トークンは **90日ローテ**。ローテ期限14日前に自動通知
- **退職・異動時は24時間以内に失効**（台帳の owner 列から対象を機械抽出）
- 認証情報を**コード・スプレッドシート・Slackに平文で置かない**（GASなら PropertiesService、n8nなら Credentials）
- 四半期に1回、**90日間未使用の資格情報を自動失効候補**として提示
**実務テンプレート**：
```yaml
# credentials-ledger.yaml
- cred_id: CRD-007
  system: Airwork
  type: api_key
  used_by: [AUT-014, AUT-021]
  scopes: [read:reports]        # 書込権限は付与しない
  storage: n8n_credentials      # 平文置き場所なし
  owner: owl
  backup_owner: bo
  issued: 2026-06-01
  rotate_due: 2026-08-30        # 90日
  last_used: 2026-08-19
```
**期待効果**：退職・キー失効による自動化の突然死をゼロ化。権限過剰による事故範囲も縮小する。

#### 6. 【シャドーIT自動化の可視化と廃止基準（自動化台帳）】
**なぜ必要か**：現場が自作した GAS・Zap は誰も把握しておらず、作者が異動した瞬間に「動いているが誰も直せない」ブラックボックスになる。08-05 の「設計外経路を塞ぐ前に実測」と同じ思想で、**禁止でなく吸収**する仕組みが要る。
**具体的手法**：自動化台帳を単一SSOTとし、①既存の棚卸し（Apps Scriptプロジェクト一覧・Zap一覧・Webhook受信元一覧の3方向から発見） ②新規は台帳登録を実行条件にする ③定期廃止レビュー、の3段で回す。
**判断基準・数値ライン**：
- 全自動化に **owner と backup_owner の2名**を必須（バス係数1を禁止）
- **90日間実行ゼロ＝廃止候補**、120日で自動停止（停止後30日はリストア可）
- **四半期棚卸し**で台帳未登録の自動化を発見したら、停止でなく**14日以内に台帳へ吸収**（現場が地下化するのを防ぐ）
- 未登録自動化の発見数を KPI 化：**四半期あたり3件以下**を目標
- 台帳には「止まったら誰が困るか（業務影響1行）」を必須記入。空欄は廃止候補扱い
**実務テンプレート**：
```yaml
# automation_registry.yaml
- id: AUT-014
  name: 月次レポート添付送付
  platform: GAS
  owner: owl
  backup_owner: bo
  trigger: schedule(毎月1日 08:00 JST)
  clients: [翔星建設, 宮村建設]
  impact_if_stopped: "月次レポート未送付＝クライアント報告が丸1日遅延"
  roi_id: AUT-014
  credentials: [CRD-007]
  last_run: 2026-08-01
  runbook: docs/runbooks/AUT-014.md
  review_due: 2026-10-01
```
**期待効果**：属人化の可視化。廃止基準があることで台帳が肥大せず、棚卸しが形骸化しない。

#### 7. 【ジョブ失敗のエラー通知設計（重大度ルーティング・集約・アクション率監視）】
**なぜ必要か**：既存の通知設計は **SLA違反（業務遅延）**が対象で、**ジョブ失敗（技術障害）**は別系統。同じチャンネルに混ぜると 06-03 で潰したアラート疲れが技術側から再発する。
**具体的手法**：重大度3段で宛先とチャンネルを分離し、同一 `job_name × error_class` は指定窓で集約して1通にする。通知には必ず run_id とリラン導線を入れる（05-26 の即時アクションリンク化を技術通知にも適用）。
**判断基準・数値ライン**：
- **P1（業務停止・クライアント影響あり）**：即時・担当＋部署長メンション・15分以内に一次応答
- **P2（リトライ中／DLQ滞留10件未満）**：15分窓で集約し1通、営業時間内のみ
- **P3（単発失敗でリトライ成功済み）**：通知せず日次サマリのみ
- **集約ルール**：同一 job×error_class は 15分窓で1通（「他N件」表記）。深夜帯（22:00〜07:00）は P1 のみ発報
- **アラート予算**：1チャンネル **1日15件**を上限とし、超過が2週続いたら閾値・集約窓を見直す
- **アクション率**（通知に対し何らかの操作が行われた割合）を月次計測し、**50%未満の通知種別は廃止 or P3降格**
**実務テンプレート**：
```
[P2] AUT-014 月次レポート添付送付 — 失敗（他3件）
run_id : 01JQ8W...  attempt 3/5（次回リトライ 12:14）
error  : HttpError 429 rate_limit  ／ 対象: 翔星建設
影響   : 未送付2件（納期 本日18:00）
👉 リラン: <link>  DLQ確認: <link>  ランブック: docs/runbooks/AUT-014.md
```
**期待効果**：通知の総量を抑えたまま P1 の検知漏れをゼロに。通知そのものを計測対象にすることで、閾値が自己修正される。

### 🚫 新たに定義したNGパターン
1. **ROI試算なしで自動化に着手する**：月10分削減の自動化でも保守は毎年発生する。ペイバック12ヶ月超は原則作らず、統制目的の例外だけを明示的に認める。
2. **リトライ間隔を固定秒（例：5秒×3回）で実装する**：相手APIが詰まっている時に同期再送を重ね、障害を延命させる。指数バックオフ＋フルジッタ以外を禁止する。
3. **4xx（429以外）をリトライ対象に含める**：認証エラー・不正パラメータは何回投げても通らず、DLQ到達を遅らせるだけ。即DLQ行きにする。
4. **DLQを作ったが誰も見ない**：退避先があること自体は防御にならない。滞留10件 or 24時間で人へエスカレーションする監視を必ず対にする。
5. **個人アカウント・個人APIキーで本番自動化を動かす**：退職・パスワード変更で全停止する。サービスアカウント実行を既定とし、例外は90日期限付き申請制。
6. **実行ログに顧客名・原価・請求金額を平文で書く**：ログは業務システムより権限が緩く、監査ログ自体が情報漏えい経路になる。キー参照＋マスキングに限定する。
7. **現場の自作自動化を見つけて即停止する**：地下化して可視化の外に落ちる（08-05の設計外経路と同じ構造）。停止でなく14日以内の台帳吸収を既定対応にする。
8. **ジョブ失敗通知をSLA違反通知と同一チャンネルに流す**：技術ノイズが業務アラートの信頼性を削る。重大度別にチャンネルと宛先を分離する。
