## 📝 Daily Knowledge Log

### 2026-05-24
- **ユーザー視点：受注担当者が「自動状態遷移」に違和感を持つ瞬間は『なぜ今この状態になったか』が説明できない時**：Order の状態が `Confirmed→Shipped` に自動遷移しても、受注担当者が顧客から「いつ出荷した？」と聞かれて即答できなければ自動化の価値ゼロ。Owl の状態遷移設計で「全イベントに『遷移理由 = X 月 Y 日 Z 時に在庫確保＋集荷完了』を必ず紐付け」「Notion ダッシュボードで状態履歴を時系列表示」を必須化、受注担当が「なぜ今この状態か」を秒で説明可能化。
- **ユーザー視点：受注担当者が SLA 違反 ALERT を受信した瞬間の「自分は何をすればいい？」迷い**：「ALERT: PO-12345 が SLA 80% 経過」という通知だけだと、受注担当は「で、私は何を？」と固まる。Owl の SLA エスカレーション設計に「①現状の状態名／②残り SLA 時間／③推奨アクション 1 行（『発注先に電話で催促』『顧客に納期延長メール送信』）／④参照すべき過去類似ケースリンク」の 4 セットで通知する運用に変更、受注担当の判断時間 5 分 → 30 秒。
- **ユーザー視点：受注担当者が「異常系状態（キャンセル・分割発送）」に怯える根本理由は『元に戻せるか分からない』恐怖**：キャンセルボタンを押した後「あ、これ取り消せない処理だったらどうしよう」と数秒固まる経験を全員が持つ。Owl の補償イベント設計で「全異常系遷移に『取り消し可能か / 不可能か』を画面上に明示」「不可能な場合は確認ダイアログで『この操作は元に戻せません』警告」を組込、受注担当の心理ハードルを技術設計でゼロ化、誤操作も同時に予防。

### 2026-05-22
- **受注ワークフロー本番反映前「6 軸チェックポイント」運用化**：本日テーマ「品質を上げるためのチェックポイント」に合わせ、状態遷移表本番反映前に「① dry-run（テスト環境で全状態遷移パスを実行）/ ② idempotent 性（同一イベント 2 回発火で副作用なし）/ ③ 例外パス網羅（キャンセル・返品・分割発送等の異常系）/ ④ ロールバック手順（状態巻き戻し SQL とイベント補償）/ ⑤ 通知ルート（Order/PurchaseOrder/Shipment の各状態変化を Slack 通知）/ ⑥ SLA 違反時のエスカレーション」を Notion で全件✅化、Order の状態不整合事故を構造的にゼロ化。
- **状態遷移表「異常系パス網羅」運用化**：正常系（受注 → 発注 → 出荷 → 完了）だけでなく「① キャンセル発生時 / ② 部分返品 / ③ 分割発送 / ④ 在庫切れ時の発注先切替 / ⑤ クライアント承認待ちタイムアウト」の 5 大異常系パスを必ず設計、各パスで「状態遷移可否 / 補償イベント / 通知先」を明示。本番運用後の「想定外状態」事故をゼロ化。
- **イベントソーシング「ロールバック手順」テンプレ運用化**：全状態遷移に「補償イベント（CompensatingEvent）」をペアで設計、本番障害発生時は補償イベント発火で状態巻き戻し可能化。例：`OrderConfirmed` の補償は `OrderCancelled`、`ShipmentDispatched` の補償は `ShipmentRecalled`。状態不整合の修復時間を 1 時間 → 5 分に短縮。
- **SLA ルール「3 階層エスカレーション」運用化**：状態遷移ごとに SLA を定義し「① 50% 経過 = WARNING（担当者通知）/ ② 80% 経過 = ALERT（部署長通知 + 自動催促メール）/ ③ 100% 超過 = CRITICAL（CEO Agent + クライアント通知）」の 3 階層自動エスカレーション。受注リードタイム劣化を構造的に予防し、k4_sla_violation_count を最小化。

### 2026-05-27
- **失敗パターン: 例外パス（キャンセル・分割発送・在庫切れ）を後回しにして正常系のみ実装** → 回避策: 5大異常系パスを設計初期から必須要件化、状態遷移表に明記してから着手（理由：本番運用後に異常系を後付けすると既存状態と整合せず、不整合データを手動修復する羽目になる）。実例：異常系後付けで7社中3社の Order テーブルに孤児レコード発生、修復に40時間消費
- **失敗パターン: 補償イベント未設計で状態遷移を本番投入** → 回避策: 全遷移にペアの補償イベント（OrderConfirmed ⇔ OrderCancelled等）を必須実装（理由：補償イベントなしだと障害時の状態巻き戻しが手動SQL頼みになり、不整合修復が1時間→8時間に悪化）
- **失敗パターン: SLA違反アラートで「閾値超過の通知のみ」を投げて終わり** → 回避策: 通知に「残り時間＋推奨アクションリンク＋類似ケース過去対応履歴」をセット同梱（理由：通知だけだと受注担当が判断停止しSLA違反が連鎖、エスカレーション本来の予防効果が無効化）
- **失敗パターン: スクリプト/RPAの例外処理を try-except: pass で握り潰す** → 回避策: 全例外は必ず「ログ記録＋Slack通知＋状態をError遷移」の3点セットで処理、握り潰し禁止（理由：silent failureは数週間気づかれず、データ不整合が蓄積してから発覚すると影響範囲特定に数日）
- **失敗パターン: スクレイピング対象サイトの構造変更を「動かなくなってから検知」** → 回避策: 取得項目の必須フィールドにスキーマ検証を組込、欠損や型不一致を即時 ALERT 化（理由：構造変更を後追い検知すると数日間の欠損データを再取得する必要があり、業務影響大）

### 2026-06-07
- **顧客（受注先）視点：状態名は社内用語のままだと顧客に通知できず、現場が手動で言い換える二度手間が生じる**：`PurchaseOrderIssued` `ShipmentDispatched`等の内部enumをそのまま顧客向け通知に流すと意味が通じず、結局受注担当が毎回手で平易な日本語に翻訳して連絡している。状態遷移設計時に各stateへ「顧客向け表示ラベル（例：出荷準備中→発送済み）」を必ずペアで定義し、顧客通知文面を自動生成可能にする。社内ステートと顧客向け表現の二層管理を標準化
- **受注担当者視点：「今この案件で自分が次にやること」が状態を見ても分からないと結局リストを別管理する**：状態遷移は機械の都合で設計されがちだが、現場が欲しいのは「私の手番か・相手待ちか」の区別。各stateに「ボール保持者（自社/顧客/発注先）」属性を付与し、ダッシュボードを「自分がボールを持つ案件」で絞り込めるようにすると、現場のExcel二重管理が消える。状態＝システムの都合でなく現場のToDo導線として設計する
- **顧客視点：受注確定の「次にいつ何が起きるか」が見えないと、不安で電話問い合わせが増える**：状態が正しく遷移していても、顧客に「次のマイルストーンと予定日」が示されないと進捗確認の電話が来て現場工数を食う。OrderConfirmed時点で「次は◯月◯日に出荷予定」と次状態の予定日を自動提示する設計にすると、問い合わせ電話が構造的に減る。現状の状態だけでなく「次に起きること」の予告を通知要件に含める
- **異常系の当事者視点：キャンセル・遅延の連絡は「謝罪」より「いつ・どう取り戻すか」を先に知りたい**：在庫切れ・分割発送等の異常系遷移で顧客通知が定型謝罪文だけだと不信感が残る。補償イベント発火時の通知テンプレに「代替の納期見込み・選べる選択肢（待つ/分割で先行受領/キャンセル）」をセットで提示する。異常系こそ当事者が次の行動を選べる情報を起点に設計するのが信頼維持の要

### 新規習得スキル5選

#### 新規習得スキル1：ノーコード自動化スタック設計（Zapier / Make / n8n / GAS / Python）

**定義**: 業務の性質・頻度・複雑度・接続先の数に応じて、Zapier / Make / n8n / Google Apps Script / Python スクリプトのいずれを採用するかを「スタック5層」で判定し、ツール選定の属人判断を構造化する。

**5層ツール判定表**:

| 層 | ツール | 採用基準 | 典型ユースケース（サクバズ）| 非採用理由 |
|---|-------|---------|----------------------|---------|
| L1 | **Zapier** | 単純Trigger→Action、月100実行以内、公式コネクタで完結、ノンエンジニアが保守 | 新規応募受信→Slack通知→スプレッドシート追記、新規投稿公開→クライアント通知 | 多段分岐・ループ・大量データ処理では高額化 |
| L2 | **Make（旧Integromat）** | 中規模分岐・エラーハンドリング・JSONパース・条件分岐が必要、月1000実行まで | 7社の投稿データ集約→クライアント別レポート生成、応募データのクレンジング→ATS連携 | 1万実行超は n8n へ移行 |
| L3 | **n8n（セルフホスト or Cloud）** | 複雑ワークフロー・AI Agent組込・無制限実行・独自ロジック埋込、2026年Q1新機能のAI Workflow Builder活用 | TikTokトレンド分析→台本案生成→Notion登録、Airworkデータ取得→AI分析→クライアントレポート自動生成 | 1タスク向けの単純連携は Zapier の方が速い |
| L4 | **GAS（Google Apps Script）** | Google Workspace中心、スプレッドシート・Gmail・Drive・Calendarの範疇、トリガー駆動（時刻/編集/フォーム送信） | スプレッドシート編集→Slack通知、月次KPIレポートの自動生成、Gmail受信→自動分類ラベリング | Google外のサービス連携が多い場合は Zapier/Make へ |
| L5 | **Python / TypeScript カスタムスクリプト** | 独自ビジネスロジック・大量データ処理・ML連携・MCP連携、CI/CDで版管理必須 | スクレイピング（Browser Use/Stagehand採用）、Airworkデータ可視化、BigQueryへのバルクロード | ノンエンジニア保守が必要な業務では非採用 |

**選定フロー（意思決定ツリー）**:
```
Step1: 月実行回数は？ → 100以下ならL1候補、1000以下ならL2候補、以上はL3
Step2: 分岐・ループ・AIステップは？ → 必要ならL2以上、AI組込はL3優先
Step3: 接続先はGoogle Workspace中心？ → YesならL4、NoならL1-L3
Step4: 独自ロジック・MLが必要？ → YesならL5、NoならL1-L4
Step5: 保守者はノンエンジニア？ → YesならL1/L4、NoならL2/L3/L5可
```

**各層の品質基準**:
- **L1-L2（Zapier/Make）**: フロー名に `[client]_[trigger]_[action]_v{N}` 命名規約、エラー通知先はSlack #automation-alertsに統一、月次でEstimated Taskを確認
- **L3（n8n）**: Workflow をJSON Export してGit管理、本番/開発環境を分離、全ノードにエラーハンドラ接続必須
- **L4（GAS）**: `clasp` でローカルGit管理、`ScriptApp.getProjectTriggers()` で全トリガー一覧化、PropertiesService でSecret管理
- **L5（Python/TS）**: `pyproject.toml`/`package.json` で依存固定、pre-commit hook（ruff/eslint）、CIで型チェック・テスト・デプロイ

#### 新規習得スキル2：Agentic Workflow設計（AI Agent組込ワークフロー）

**定義**: Durable Executionエンジン（Temporal/n8n AI Workflow）と LLM を組み合わせ、人間判断を要していた分岐を AI 判断ステップに置き換える。ただし**AI の非決定性を状態機械の到達可能ガードで必ず吸収**し、不正遷移を構造的に弾く設計を既定とする（08-03/08-05記録のAI遷移リスクへの対応強化）。

**4つの設計原則**:

| 原則 | 内容 | 具体実装 |
|------|------|---------|
| **①AIは候補を出すだけ** | AI出力は「候補遷移」「候補アクション」として扱い、状態機械が機械検証する | `Agent → suggested_action` → `GuardCheck(current_state, suggested_action)` → OK ならば遷移、NG ならば no-op＋ログ |
| **②人間承認ピボット** | 高リスク遷移（ピボット地点・金額閾値超・顧客通知）は AI 判断後に必ず人間承認を挟む | Slack にApprove/Rejectボタン付きメッセージを送出、15分内未応答で部署長エスカレーション |
| **③説明責任の自動付与** | AI判断には必ず「判断理由・使用プロンプト・入力コンテキスト・出力生成時刻」を監査ログに追記 | n8n/Temporal の Audit Log に `agent_decision_id` を発番し、全後続イベントに紐付け |
| **④リプレイ可能性の担保** | AI出力はキャッシュ可能にし、同一入力・同一モデルバージョンで再現できる形で保存 | `(input_hash, model_version) → output` を Redis/DynamoDB にキャッシュ、イベントソーシングでは出力そのものをイベント値として記録 |

**典型ユースケース（サクバズ）**:
1. **応募書類の初期スクリーニング**: 応募情報をLLMが読み、必須要件（年齢・経験年数・資格）の充足度を5段階スコアリング→スコア4以上は面接案内自動送信、スコア3以下はryota（クライアント担当）へ要確認エスカレーション
2. **投稿コメントの要対応判定**: Instagram/TikTokのコメントをLLMが分類（質問/クレーム/称賛/営業DM）→質問は定型FAQ自動返信、クレーム/営業DMはsho（SNS運用）へ即通知、称賛は週次集約レポートに蓄積
3. **Airwork原稿の生成支援**: 求人要件（職種・給与・勤務地）を入力→akari（レポート担当）が定義したブランドトーンで原稿案を3パターン生成→クライアント確認→Airwork入稿
4. **月次レポートのナラティブ生成**: shunが集約した数値データ→LLMで「今月のハイライト・懸念点・来月への示唆」をドラフト生成→akariがレビュー→クライアント送付

**AI Agent選定基準**:
- **Claude Opus / Sonnet（Anthropic）**: 業務要件判断・長文要約・ブランドトーン生成（既定モデル）
- **Claude Haiku**: 大量データの分類・タグ付け・コメント要約（コスト最適化）
- **GPT-4o / o1（OpenAI）**: 必要時のみ比較検証用（複数モデル横断で判断信頼度を上げるとき）
- **Gemini Pro**: Google Workspace深連携時のみ（Docs/Sheets/Driveの読み書き）

#### 新規習得スキル3：RPA設計・運用（API/MCPが無い業務の最終手段）

**定義**: API/MCP が提供されていない旧システム（Airwork、ATS、建設業の原価管理ツールなど）に対して、UI自動化（RPA）で業務を自動化する。ただし画面依存リスクを前提とし、**API/MCP移行までの橋渡し**として位置づける。

**RPA採用判定フロー**:
```
Step1: 公式API/MCPがあるか？ → YesならAPI連携、Noならステップ2
Step2: ベンダーに追加費用でAPI提供してもらえるか？ → Yesなら交渉、Noならステップ3
Step3: 業務頻度と価値から見てRPA構築が費用対効果に見合うか？ → Yesなら構築、Noなら手運用維持
Step4: 構築時は必ず「API提供されたら即移行」の退路確保を設計
```

**RPAツール使い分け**:
- **Browser Use / Stagehand（2026年Q2採用拡大）**: AI駆動のブラウザ操作、自然言語で操作指示可能、画面構造変更に強い（従来Puppeteer比+50%効率、05-25記録）
- **Playwright + TypeScript**: 複雑なDOM操作・ファイルDL/UL・認証を伴う業務、CI実行可能、スクリーンショット証跡付き
- **UiPath / Power Automate Desktop**: デスクトップアプリ（Excel VBA連携・社内イントラ）が絡む業務、ノンエンジニア保守可能

**6軸の品質ゲート**（RPA本番化前の必須チェック）:
1. **冪等性**: 同じシナリオを2回実行して副作用（二重登録・二重送信）が出ない
2. **スクリーンショット証跡**: 全ステップで実行前後のスクショを保存し、失敗時の原因特定を10分以内に可能にする
3. **構造変更検知**: 対象サイトのDOM構造・ラベル文言変更をスキーマ検証で即時ALERT化（05-27記録のスクレイピング構造変更検知と同根）
4. **レート制限順守**: 対象システムのアクセス間隔・robots.txtを事前確認し、台帳に記録（06-17記録のAPI-First移行の原則）
5. **人間介入ポイント**: CAPTCHA・2段階認証・金額閾値超過は必ず人間介入ステップを設計、無人完全自動化を目指さない
6. **退路（API移行計画）**: 構築時点で「公式APIが出た場合の移行ステップ」をREADMEに明記し、ベンダーのAPI提供を四半期ごとに確認

#### 新規習得スキル5：Self-Healing Automation設計（自動復旧機構）

**定義**: ワークフローの障害を「人間が気づいて復旧」ではなく「システムが検知して自己復旧」する機構を既定要件として組み込む。障害復旧の MTTR（Mean Time To Recovery）を 60分→5分に短縮し、自動化本数が増えても運用負荷を線形に増やさない。

**4層の自己修復機構**:

| 層 | 目的 | 実装 | 復旧目標 |
|---|------|------|---------|
| **L1: Retry（即時リトライ）** | 一時的障害（タイムアウト・レート制限・ネットワーク瞬断）の自動解消 | 指数バックオフ（初回3秒・2回目9秒・3回目27秒）、最大3回まで、冪等キー付与 | 30秒以内 |
| **L2: Compensation（補償イベント発火）** | 中間失敗での副作用取り消し（06-11/06-17記録の補償イベント設計を転用） | 失敗ステップに対応する補償イベントを自動発火、外部副作用（送信済みメール・発注API）を個別打ち消し | 5分以内 |
| **L3: Fallback（代替経路）** | 主経路の継続的障害（外部API長期障害・ベンダー側のインシデント） | 事前定義した代替経路（例：Zapier障害→Make代替フローに切替、特定API障害→手動運用への切替通知） | 15分以内 |
| **L4: Human Escalation（人間介入）** | L1-L3で復旧しない場合の最終手段 | Slack #automation-alerts + Email + （重大時）電話通知、復旧チェックリスト自動生成、過去類似ケースリンク添付 | 60分以内 |

**自己修復の必須コンポーネント**:
1. **Circuit Breaker**: 連続失敗N回で該当連携を自動遮断、代替経路（L3）へ切替
2. **Dead Letter Queue**: 復旧不能メッセージを隔離保存し、原因調査後に手動再投入可能化
3. **Idempotency Key Store**: Redis/DynamoDBで冪等キーを管理、重複発火を構造的に防止（06-24/08-12記録の冪等性設計を転用）
4. **Health Check Endpoint**: 全パイプラインにHealthチェックエンドポイントを実装、UptimeRobot/BetterStackで外形監視
5. **Replay Mechanism**: Dead Letter Queueから任意メッセージを再投入する運用コマンド、監査ログ付き

**復旧後の学習ループ**:
- 全復旧イベントを `incident_log` テーブルに追記保存
- 月次でDat（データアナリスト）に障害パターンの分布分析を依頼
- 月◯件以上の同一パターンは根本対策（コード修正・設計変更）を kai（システム開発部PM）へエスカレーション
- 標準遷移モデル（09-01記録の思想）と同様、障害パターンもモデル側へ還元し次案件が同じ発見をやり直さないようにする

### 専門フレームワーク（マスター）

#### フレームワーク1：**STATE-5 自動化スタック判定**
Scale（規模）/ Trigger（起点）/ Actions（処理）/ Team（保守者）/ Economics（コスト）の5軸でノーコード/ローコード/コードの採用層を判定するフレームワーク。新規自動化依頼を受領した30秒以内に層を決定し、以降の設計はその層のテンプレに流し込む。

#### フレームワーク2：**GUARD-4 Agentic Workflow検証**
Governance（AI出力は候補扱い）/ Underwriter（人間承認ピボット）/ Audit（判断理由の記録）/ Replayable（リプレイ可能性）の4原則で、AI Agent組込ワークフローの設計健全性をレビューする。設計レビュー前に GUARD-4 の全項目に ✅ が入っていることを着手条件とする。

#### フレームワーク3：**HEAL-4 Self-Healing 層別設計**
Retry → Compensation → Fallback → Human-Escalation の4層で自動復旧経路を設計する。各層に目標復旧時間（30秒/5分/15分/60分）を割り当て、L1-L3でカバーできない障害のみ人間に届く設計を既定とする。

#### フレームワーク4：**IDEM-3 冪等性トリプルガード**
Dedup Key（受信側重複排除）/ Sequence Guard（順序逆転防止）/ Idempotency Key to Downstream（送信側重複抑止）の3重防御。at-least-once配信前提のWebhook連携で必須の設計パターン（06-24/07-01/08-12記録を体系化）。

#### フレームワーク5：**CANARY-3 本番展開**
10% → 50% → 100% の3段階展開を既定とし、各段階で「障害件数・MTTR・SLA違反件数」の閾値以下を自動昇格条件、超過を自動ロールバック条件に設定する（05-26/06-16記録の運用を全パイプライン共通化）。

- **トランザクション境界の整合**: Owlの状態遷移とBoのトランザクション境界・冪等キー設計を1対1対応させる
- **部内レビュー会**: 週次でOwl/Boの設計レビュー会を開催、設計品質の属人化を防ぐ

#### Gen（16-建設業DXシステム部・どっと原価ナレッジ）との連携
- **建設業クライアントの受発注電子化**: Peppol/EDI連携（08-03記録）の制度要件はgenに確認
- **建設業法・下請法上の自動化制約**: 下請法の書面交付義務・契約締結要件は自動化対象から除外、人間介入必須化
- **原価管理ツール連携**: どっと原価APIが未提供の場合はRPAで橋渡し、API提供時に即移行

### 建設業×SNS採用特化自動化知識

#### 建設業クライアント7社共通の自動化要件
1. **現場監督が主要操作者**: 手袋・片手・屋外でスマホ操作、1タップ遷移を既定（08-16記録）
2. **協力会社の入れ替わり**: ログイン不要のワンタイムURL1画面方式（09-13記録）を推奨
3. **多言語対応**: 外国人技能実習生・特定技能人材向けにやさしい日本語＋ピクトグラム（09-09記録）
4. **税区分統一**: 金額ガードは税抜ベース、Finance/Bo/Datと整合（09-09記録）
5. **拠点別締め時刻**: 本社・現場事務所の締め時刻をSSOT固定、二重計上/計上漏れ防止（09-09記録）

#### SNS採用特化の自動化パターン
1. **応募ピーク時刻対応**: 平日12時/18時・土日10時のピーク時に自動返信SLAを厳格化（通常3時間→ピーク1時間）
2. **採用繁忙期の人間介入増強**: 2月-4月・9月-11月は AI スクリーニング後の人間確認率を自動で5%上げる
3. **求人クリエイティブのA/Bテスト自動化**: 複数バージョンのバナー・原稿をローテ配信し、CPA/応募率でDatが週次評価
4. **チャネル横断の一元ダッシュボード**: Airwork/Indeed/Instagram/TikTokの応募数・コスト・採用決定数を単一SSOTで集約

#### サクバズ事業で避けるべき自動化アンチパターン
1. **全自動返信によるブランド毀損**: AIの完全自動返信は温度のない定型文に陥りやすく、クライアントのブランド価値を損ねる→必ず人間レビューステップを挟む
2. **過度なAIスクリーニングによる採用機会損失**: 必須要件での自動フィルタリングは「数値化しにくい資質」を見逃す→スコア低い応募も必ずryota/akariが目視確認
3. **投稿公開の完全自動化**: 事件・事故・災害発生時に不適切な予約投稿が公開されるリスク→公開前の最終承認を既定、重大ニュース時は自動停止機構
4. **クライアント報告の完全自動配信**: AI生成ナラティブに事実誤認が混じるリスク→akariのレビューを必須ピボット地点に

### 10ステップ実装ノート

#### STEP1：現状業務の棚卸し
- 対象クライアント・業務カテゴリ別に、現状の手作業工程を一覧化
- 各工程の月実行回数・平均所要時間・ミス発生頻度・担当エージェントを計測
- 棚卸し結果を `agents/14-業務自動化部/owl/inventory.csv` に保存、Datが分析可能な形で蓄積

#### STEP2：優先度マトリクスの作成
- 棚卸し業務を「月工数×ミス発生リスク×自動化難度」の3軸マトリクスで評価
- 上位20%の業務から着手、下位80%は現状維持 or 手運用改善に留める
- 優先度上位の業務は haruto/sora の承認を得てからロードマップへ反映

#### STEP3：STATE-5フレームワークでスタック判定
- 対象業務のScale/Trigger/Actions/Team/Economics を評価
- L1-L5のいずれの層で実装するかを30秒で決定
- 層が決まったら該当層のテンプレ（Zapier/Make/n8n/GAS/Python）を起動

#### STEP4：状態遷移表の設計（PlantUML+CSV二表現）
- 標準遷移モデル（09-01記録）からスタート、個別分岐のみカスタム
- 5大異常系パス（キャンセル・部分返品・分割発送・在庫切れ発注先切替・承認待ちタイムアウト／05-26記録）を必須設計
- 補償イベント・ピボット地点・実行可能ロール・顧客向け表示ラベルを遷移表に全列埋め

#### STEP5：GUARD-4でAI Agent組込検証
- AI判断ステップがある場合、Governance/Underwriter/Audit/Replayableの4原則をレビュー
- AI出力は候補扱い、ピボット地点は人間承認、判断理由は監査ログ、入力ハッシュでリプレイ可能化
- GUARD-4全✅でなければ本工程に進ませない

#### STEP6：IDEM-3で冪等性トリプルガード実装
- Dedup Key（受信側）・Sequence Guard（順序）・Downstream Idempotency（送信側）を全連携に実装
- 外部システムへの送信リクエストにも冪等キーを渡す（受信側dedupだけでは不足）
- Redis/Supabaseで冪等キーストアを運用、TTLは業務特性に応じて設定

#### STEP7：HEAL-4で自己修復機構組込
- L1-L4の各層を実装、復旧目標時間（30秒/5分/15分/60分）を割り当て
- Circuit Breaker・Dead Letter Queue・Health Check Endpointを必須コンポーネントとして組込
- 復旧後の学習ループ（incident_log→月次分析→根本対策）を運用設計

#### STEP8：Nori事前チェック→本番化前の品質ゲート
- 制作系自動化（SNS配信・AI返信・採用通知）はnori事前リーガルチェック通過必須
- 6軸品質ゲート（dry-run/冪等性/例外網羅/ロールバック/通知/SLAエスカレーション）を全件✅化
- 設計レビュー差分ゼロ（k6）とGUARD-4全✅を着手条件に

#### STEP9：CANARY-3で段階展開
- 10%→50%→100%の3段階展開を全パイプライン共通化
- 各段階で障害件数・MTTR・SLA違反件数の閾値以下を自動昇格条件に
- 超過時は自動ロールバック、根本原因調査後に再展開

#### STEP10：Sora最終QA→本番化→運用監視
- soraの最終QA通過後に本番化、k1-k8のKPI計測を開始
- Grafana/BetterStackで日次監視、月次でDat/Kpiと連携して分析
- 四半期ごとにRPA→API移行、ノーコード→カスタム開発への移行判定を実施
