### 2026-05-03
- **「データは正確 ≠ アクション結論が見える」の落し穴**：Airwork応募数、GA4到達率、CVRなど数値は正確に報告しても、クライアント採用担当者から「で、何を変えればいいですか？」という質問が返ってくることが多い。根因：グラフ・表は「事実の提示」に過ぎず、「どの数値が悪い → なぜ悪い → 何をする」というストーリーラインが欠ける。改善：数値毎に「評価（良い/悪い）」「原因仮説」「推奨施策」を1行セットで添記。表の下に「意思決定フロー」（例：応募CVRが低い → LP滞在時間が短い → ファーストビューの訴求見直し）を記載することで、クライアントが「理解 → 判断 → 実行」へ進む。
- **グラフの「見やすさ」と「正確性」の二律背反**：折れ線グラフをY軸0-1000でスケーリングすると、微小な変動が誇大に見える。一方、Y軸を自動スケーリングすると、元のデータの正確な比率が見える。クライアントの意思決定を支援する観点では、「軸の選択理由を明示する」ことが信頼につながる。回避策：グラフの下に「Y軸範囲：0-1000に固定→月間最大応募数を基準に設定」のように、スケーリング判断を明文化。
- **Akari・Ryota への「前置き」の重要性**：Akariにデータテーブルを渡す際、計算式・条件・仮定（「外れ値除外n=3」「サンプル数1000未満は集計外」）を省略すると、Akariが独自判断で数値を修正してレポート品質が劣化。Ryotaに渡す場合も「クライアントには『応募CVRが前月比-8%だが、流入品質の改善余地あり』と説明してください」と前置きしないと、数字だけが一人歩きしてクライアント信頼を損なう。回避策：全成果物に「読み手への前置き・背景」を1段落追加。

- **同意モード（Consent Mode v2）とCookie規制でGA4が欠損をモデル補完する運用が標準化**：同意しないユーザー分をGA4が機械学習で推計する「コンバージョンモデリング」が前提になり、実測値と推計値が混在する。応募CVRの分母（2026-06-11参照）に推計セッションが混ざる点を注記し、Airwork実数（フォーム送信）を正として突合する二重管理が必須に。

### 2026-08-03
- **インクリメンタリティ検証（ジオリフト/地域分割実験）が広告効果測定の主軸に**：個人単位アトリビューションの限界（2026-06-20参照）を、地域や期間を分けた擬似実験で「その媒体を止めたら応募が何件減るか」を測る手法が軽量ツール化。MMM（2026-07-27参照）の補完として7社規模でも「エリア分割の前後比較」で媒体の増分効果を近似でき、相関を因果と誤報告する事故（2026-07-01参照）を構造的に回避できる。

- **Microsoft ClarityのAIファネル/要約機能が拡張**：ヒートマップに加え離脱ステップのAI要約が実用化。ただしClarityはサンプル抽出でn＜30は参考値（2026-06-17参照）、デッドクリックはHanaの操作性フラグと突合（2026-07-16参照）してから提案にする原則は変わらず、AI要約も反証データ探索（2026-07-03参照）で裏取りする。

### 2026-08-05
- **（よくある失敗）棒グラフの縦軸をゼロ始まりにせず、わずかな変化を大幅改善に見せてしまう**：軸を途中から切ると数%の差が「激増」に見え、経営者が過大な期待を持つ。回避策：量の比較（応募数・件数）の棒グラフはゼロ基線を原則とし、やむを得ず切る場合は軸の破断を明示。変化率を語りたい時は折れ線＋前年同月比の注記で見せ方の誇張を排除する。
- **（よくある失敗）前月比を営業日数・祝日数の違いを補正せず比較し、2月やGW・お盆月を「応募が減った」と誤判定する**：営業日が少ない月は総数が下がって当然で、施策の失敗と誤読する。回避策：応募数・流入の前月比は「1営業日あたり平均」で比較するか営業日数・祝日数を併記し、Dengの稼働日マスタ（Deng 2026-06-17参照）と揃えて、増減は営業日補正後に評価する。
- **（よくある失敗）1件の大型流入・bot・社内アクセスを除外せず平均を歪め、CVRや滞在時間を誤報告する**：外れ値1件で平均が跳ね実態と乖離する。回避策：平均だけでなく中央値・分布（ヒストグラム）を併記し、GA4は社内IP・bot・自己参照を除外フィルタ設定。異常な1日はイベント要因メタ（Deng 2026-06-07参照）で注記し移動平均で均す。
- **（よくある失敗）統計的に有意な差を、実務的にはほぼ無意味な微差でも「効果あり」と報告する**：nが大きいと0.1%の差でもp<0.05になり、施策採用の根拠として誇張される。回避策：有意性（p値）と効果量（実務インパクト＝応募換算で何件・いくらの差か）を必ず分けて報告し、「統計的に有意だが実務的には応募0.3件/月で投資回収に満たない」と実務判断まで添える（検定力の注記、2026-07-11参照とセット）。

### 2026-08-12
- **（よくある失敗）10媒体・複数セグメントを個別にp検定し、多重比較で偶然1つが有意になったのを「効いた媒体」と報告する**：セグメントを増やすほど偶然の有意が混じり、AB判定ゲート（2026-05-27参照）を通っても偽陽性が残る。回避策：セグメント横断で同時に検定する場合はBonferroni／FDR補正で有意水準を調整し、探索的に見つけた有意は別期間の確認テストで再現を取ってから施策根拠にする。「1回の分析で見つけた勝ちセグメント」は仮説であって結論でないと明記する。
- **（よくある失敗）応募単価（CPA）を媒体ごとの費用計上基準（掲載料のみ／運用費・制作費・人件費込み）を揃えずに横並び比較し、見かけ上安い媒体へ予算を誤配分させる**：分子の費用範囲が媒体で違うと単価比較が成立しない。回避策：CPAは「分子に含める費用範囲」を媒体間で統一定義してから比較し、Ryota提案では費用内訳（掲載料＋運用費＋制作費の含有）を注記、数値の出所はDengのカタログメタ（2026-06-11参照）と接続する。ROAS/ROIの定義差（2026-05-16参照）と同型の落とし穴。
- **（よくある失敗）2軸グラフ（デュアルY軸）で無関係な2指標を重ね、軸スケールの取り方で「連動している」ように見せて相関を演出してしまう**：2軸は左右のスケールを任意に取れるため、いかなる2系列でも「重なって動く」絵を作れる。回避策：2軸グラフは因果・相関の誤読を生むため原則使わず、関係を主張するなら散布図＋相関係数＋交絡因子チェック（2026-05-13参照）で裏取りし、相関と因果を分けて言語化（2026-06-20参照）する。
- **（よくある失敗）A/Bテストの割当比が設計（50/50）と実測でズレるSRM（Sample Ratio Mismatch）を見逃し、計測バグ・混入のあるテスト結果を有効として採用する**：割当比の逸脱はリダイレクト漏れ・bot偏り・タグ二重発火（2026-07-01参照）のサインで、結果全体が信用できない。回避策：AB判定の前に割当実測比をカイ二乗でSRM検査し、有意にズレたら結果を破棄して原因を潰してから再試験する。p値＋効果量＋必要n判定（2026-06-16参照）の前段ゲートとしてSRM検査を組み込む。

### 2026-08-13
- **DengへAB判定前に「割当ログのbot・社内IP除外済みか」を確認してからSRM検査に入る**：SRM（割当比の逸脱）が有意に出た時（2026-08-12参照）、原因はリダイレクト漏れ・bot偏り・タグ二重発火（Deng 2026-07-01参照）のことが多い。Dengが提供する割当ログにbot/社内IP除外フラグが付いているかを判定前に確認し、SRMが出たら自分の集計を疑う前にDengのタグ実装を疑って原因を潰してから再試験する。計測起因のノイズと施策効果を切り分ける入口をDeng連携で固める。
- **施策効果はp値でなく「応募換算で月何件・いくら」の実務インパクトに換算してRyotaへ渡す**：統計的有意性だけ報告するとRyotaはクライアント経営者の「で、いくら？」に即答できない。有意性（p値）と効果量を分け（2026-08-05参照）、効果量を「応募換算◯件／月・CPA換算◯円」の実務言語に翻訳してRyota向けサマリーに併記する。Ryotaはそれを経営者向け翻訳（Ryota 2026-05-15参照）にそのまま乗せられ、決断スピードが上がる。
- **LPのマイクロファネル離脱段階を特定したら、段階別に差し戻し先を振り分けて渡す**：全体CVRだけでなく、スクロール到達→CTA表示→フォーム開始→送信のどの段階で落ちているか（2026-07-11参照）まで分解し、フォーム入力途中の離脱ならKotone（コピー）・Ren（実装）、CTAまで未到達ならSota（デザイン）・Hana（構造）、と離脱段階に応じて改善依頼先を名指しで振り分ける。「CVRが低い」の丸投げでなく、どの部署が何を直すかまで添えると手戻りが減る。
- **Akariへ渡す分析コメントには「速報／確定ラベル＋分母定義」を必ず添える**：Akariがレポート本文で確定前の数値を断定表現にすると、Ryota経由でクライアントに出た後の翌日訂正になる。Ryotaへの数値ラベル運用（2026-07-16参照）と同じ基準を分析コメントにも適用し、各数値に速報/確定と分母（セッション／ユーザー・JST・除外条件）を添えて、Akariが表現の強度を数値の確定度に合わせられるようにする。

### 2026-08-16
- **建設業の経営者は率でなく人数で採用を記憶しているので、CVRは必ず実人数に翻訳して置く**：「CVR2.1%→2.6%」は読み手の頭の中で何も動かないが、「求人を100人が見て応募が2人→3人に増えた」「月間で応募+4件」と人数に直すと、面接した人の顔と結びついて意思決定が起きる。率は媒体間比較のための内部言語、人数はクライアント向けの表示言語と割り切り、Akari向けコメントには率と実人数を必ず並記する。少数母数の%は誇張になる（Akari 2026-08-05参照）という問題の裏返しでもある
- **Clarityの録画は「離脱率」より説得力があり、求職者の指の動きをそのまま経営者に見せた方が改善が通る**：応募フォームの離脱を数値で説明しても「フォームが長いだけでは？」で議論が止まるが、現場職の求職者がスマホで志望動機の自由記述に到達して数十秒スクロールしたまま離脱する録画を1本見せると、設問削除の合意が即座に取れる。統計は反論の余地を残すが、実ユーザーの行動観察は当事者の直感に直接届く。n＜30は参考値（2026-06-17参照）の制約は残るため、録画は「仮説の提示」として使い、削除の効果はAB（SRM検査つき、2026-08-12参照）で確認する
- **ダッシュボードの初見ユーザーは期間フィルタの現在値を確認しないまま数字を読む**：Looker Studioを共有すると、前回の閲覧状態や既定の期間のまま「応募が激減した」と誤読され、Ryotaに問い合わせが飛ぶ。タイトル部にフィルタ連動のテキストで「2026年7月1日〜7月31日（JST・確定値）」を焼き込み、期間・集計基準・確定状態が数字と同じ視野に入る配置にする。操作を前提にした設計は、月に1度しか開かない読み手には成立しない
- **分析コメントの「◯◯が悪い」は担当者に自分の仕事の否定として読まれ、そこで読むのが止まる**：クライアント窓口は求人票を書いた本人であることが多く、原因指摘型の文章は防御反応を生んで施策提案まで届かない。同じ内容を「求人票の給与欄をレンジから実額のモデル例に変えると、同商圏の相場（Rui連携）比で応募が月◯件増える見込み」と未来形・効果量つきに書き換える。効果量を実務言語に翻訳する運用（2026-08-13参照）は、Ryota向けだけでなく読み手の心理的な受け取りやすさにも効く

### Step 3: 追加すべきコアスキル（5選）

#### Core-1: 因果推論の実務適用（DiD / PSM / Synthetic Control / Geo-lift）
- **なぜ必要か**：採用広告はA/Bテストできない場面が多い（求人票は1本しか出せない、媒体は同時に複数出稿している）。観察データから因果を取り出す技術がないと「相関を因果と誤報告する事故」（2026-07-01参照）を注意喚起でしか防げない。
- **習得内容**：
  - **DiD（差分の差分法）**：媒体を追加した店舗/エリア vs 追加していないエリアの応募数推移を比較。**平行トレンド仮定**の事前検証（施策前3〜6ヶ月のトレンド一致）を必ず図示する。
  - **PSM（傾向スコアマッチング）**：求人票の条件（給与・勤務地・職種・掲載期間）が異なる案件同士を、傾向スコアで揃えてから比較。**共変量バランスの確認（SMD < 0.1）**を報告に含める。
  - **Synthetic Control**：1クライアントだけ施策を打った場合、他6社の加重合成で「打たなかった場合の宮村建設」を作り比較。n=1でも因果効果を推定できる唯一の実用手段。
  - **Geo-lift（地域分割実験）**：商圏を分けて片方だけ配信停止。2026-08-03 の知見を**実行可能な手順**に落とす。
- **到達目標**：媒体別の増分効果（incremental applications）を、点推定＋信用区間つきで四半期に1回提示できる。

#### Core-2: ベイズA/Bテストと階層ベイズ（小サンプルの意思決定）
- **なぜ必要か**：LET のクライアント規模では月間応募が10〜50件。頻度論のA/Bでは必要nに永遠に到達せず（2026-06-16参照）、「判断できません」で終わる。ベイズなら**サンプルが少なくても「Bが優れている確率78%、期待損失0.4件/月」という意思決定可能な形**で出せる。
- **習得内容**：
  - Beta-Binomial 共役事前分布による CVR 比較（`P(B>A)`、期待損失、HDI）
  - **階層ベイズ（partial pooling）**：7社のデータを完全分離せず部分共有し、データの少ないクライアントの推定を全体傾向で補強（shrinkage）。小規模クライアントの外れ値的CVRを過大評価しない。
  - 事前分布の設定根拠を必ず明記（無情報 or 過去実績ベース）。恣意性の批判に耐える形で。
  - MAP（Multi-Armed Bandit）は**採用広告では原則使わない**判断も含めて理解する（学習期間中の機会損失より、明確な判定と説明可能性を優先する案件が多い）。
- **到達目標**：n＜30 でも「参考値」で逃げず、確率表現で意思決定材料を出す。

#### Core-3: Analytics Engineering（SQL / dbt / データモデリング）
- **なぜ必要か**：現状 G1。分析が手作業＝再現不能＝監査不能＝スケールしない。指標定義が人の頭にあるうちは、Shun が不在の月にレポートが崩れる。
- **習得内容**：
  - **BigQuery**：ウィンドウ関数、`QUALIFY`、配列/構造体（GA4のBigQueryエクスポートは `event_params` がネスト構造）、パーティション/クラスタリングによるコスト管理
  - **dbt**：staging（媒体別生データ正規化）→ intermediate（ファネル結合）→ marts（クライアント別月次指標）の3層構造。`dbt test`（not_null / unique / accepted_values / 独自の分母整合テスト）で**データ品質をCIで担保**。
  - **指標のセマンティックレイヤ化**：「応募CVR」の分母定義（2026-07-02参照）を YAML に記述し、全レポートが同一定義を参照。定義変更は Pull Request で履歴に残る。
  - **冪等性**：同じ入力で何度実行しても同じ結果。月次バッチの再実行が怖くない状態。
- **到達目標**：「その数字どう出した？」に、Slackの説明ではなく**コードのURL**で答えられる。

#### Core-4: 時系列予測とシナリオシミュレーション
- **なぜ必要か**：G4。Haruto（経営企画）の事業計画、Ryota の提案書に「見込み数値」を供給できると、Shun の役割が「振り返り」から「意思決定の前工程」に移る。
- **習得内容**：
  - **Prophet**：週次・年次季節性と休日効果（日本の祝日・GW・お盆・年末年始）を明示的にモデル化。採用は季節性が極めて強い（新年度前・ボーナス後の転職期）ため相性が良い。
  - **SARIMA / 状態空間モデル**：Prophet が過剰適合する短系列でのベースライン比較用。
  - **バックテスト必須**：`cross_validation` で MAPE / MAE を出し、**予測の精度を数値で開示**する。精度不明の予測は出さない。
  - **予算シナリオ**：媒体別の投下額→応募数の逓減曲線（Hill/adstock）を推定し、楽観・標準・悲観の3シナリオで応募数レンジを提示。
- **到達目標**：月次レポートに「翌月予測（信頼区間つき・過去6ヶ月のMAPE併記）」を標準搭載。

#### Core-5: データストーリーテリングと可視化設計（Tufte / Knaflic）
- **なぜ必要か**：分析の正しさと、意思決定が起きるかは別問題。2026-08-16 の知見（率→実人数、Clarity録画の説得力、否定形を未来形に書き換え）を**体系化して全納品物に適用**する。
- **習得内容**：
  - **Tufte**：data-ink ratio 最大化、chartjunk（3D・グラデーション・不要な枠線）排除、**small multiples**（媒体別トレンドは7個の小グラフを同一軸で並べる＝比較が一瞬で終わる）、sparkline を表に埋め込む
  - **Knaflic の6ステップ**：①文脈理解（誰に何を決めさせたいか）②適切な表示形式③不要な要素の排除④注意の誘導（色は1色だけ強調、他はグレー）⑤デザイナー的思考⑥ストーリー化（起・承・転・結）
  - **Big Idea 1文ルール**：レポート冒頭に「このレポートで決めてほしいこと」を1文で。例：「Indeed の予算を月8万円 → 12万円に増やすべき」
  - **アクセシビリティ**：色覚多様性に配慮（赤緑の対比を避ける／形状・ラベルでも判別可能に）、印刷（白黒）でも読める設計
  - **禁止事項の明文化**：2軸グラフ原則禁止（2026-08-12参照）、量の棒グラフはゼロ基線（2026-08-05参照）、円グラフは3要素以下、3Dは全面禁止
- **到達目標**：グラフを見た経営者が説明なしで結論に到達する。

### Step 5: 追加フレームワーク・方法論

#### F1. 分析依頼の受付フレーム「DAR（Decision-Action-Result）」
```
どんな依頼も、着手前に必ず3つを埋める。埋まらない依頼は着手しない。
  Decision : この分析の結果、誰が何を決めるのか？
  Action   : 決めた後、具体的に何をするのか？
  Result   : それで何の数字がどれだけ動くと期待するのか？

例）NG依頼「先月のデータまとめて」
    → DAR埋め: Decision=Ryotaが宮村建設に来月の媒体配分を提案する
               Action=Indeed予算を増やすかIndeed停止してAirwork集中か
               Result=応募数を月8件→11件へ
    → 必要な分析が「媒体別の増分効果」だと確定する。集計作業は不要。
```

#### F2. 仮説検証の型「PICOT+（採用データ版）」
```
P (Population)  : 対象は誰か（宮村建設・土木職・スマホ流入のみ 等）
I (Intervention): 何を変えるか（給与欄をレンジ→実額モデル例に）
C (Comparison)  : 何と比べるか（変更前3ヶ月 / 他6社の同期間トレンド）
O (Outcome)     : 主要指標は1つに絞る（応募完了数／セッション）
T (Time)        : いつからいつまで（営業日補正済み・JST・確定値）
+ (Threat)      : 想定される交絡は何か（季節性・競合の同時出稿・媒体アルゴ変更）
```

#### F3. 因果の階段（Ladder of Causation / Pearl）
```
Lv1 関連 (Association)   : 「Indeedが多い月は応募も多い」← 現状の多くの報告はここ
Lv2 介入 (Intervention)  : 「Indeedを止めたら応募はどうなるか」← DiD/Synthetic Control/Geo-lift
Lv3 反実仮想 (Counterfactual): 「あの月Indeedを止めていたら応募は何件だったか」← CausalImpact

報告書には必ず「この結論は Lv◯ です」と明記する。
Lv1 の結果を Lv2 の言葉（「効いた」「増やした」）で書かない。
```

#### F4. 指標設計「North Star + Guardrail + Counter」
```
North Star : 採用の質を含む最終指標（例：入社後3ヶ月定着した採用人数／月）
Input      : North Star を動かす手前の指標（応募数・書類通過率・面接設定率）
Guardrail  : 悪化させてはいけない指標（応募単価CPA、辞退率、採用担当の工数）
Counter    : North Star をハックすると悪化する指標（応募数を追うと応募の質が落ちる → 面接設定率）

原則：Input を改善する施策は、必ず Counter とセットで評価する。
      「応募が増えました」だけの報告は禁止。面接設定率・入社率を必ず併記。
```

#### F5. 実験判定のゲート順序（固定・スキップ不可）
```
Gate 0: SRM検査（割当比のカイ二乗）          → 有意にズレたら結果破棄（2026-08-12参照）
Gate 1: データ品質（bot/社内IP除外・欠測率）  → Deng に確認（2026-08-13参照）
Gate 2: 検出力（必要n到達 or ベイズで代替）   → 未到達なら頻度論の判定をしない
Gate 3: 多重比較補正（FDR/Bonferroni）        → セグメント横断検定時は必須
Gate 4: 効果量の実務翻訳（応募換算◯件・◯円） → p値だけの報告は禁止（2026-08-05参照）
Gate 5: 反証データ探索（逆の結論を支持する切り口を1つ以上探す）（2026-07-03参照）
```

#### F6. 可視化チェックリスト「TUFTE-7」（納品前に必ず通す）
```
T: Title が結論（「媒体別応募数」ではなく「Airworkが応募の7割を占める」）
U: Unit と分母を軸ラベルに明記（応募完了数／セッション・JST・確定値）
F: Fake排除（2軸禁止・ゼロ基線・3D禁止・面積誤用禁止）
T: Trim（chartjunk削除。グリッド線は薄く、枠線・影・グラデは削除）
E: Emphasis（強調は1色のみ。他はグレー。凡例より直接ラベル）
-7: 7要素ルール（1グラフの系列は7本まで。超えたら small multiples に分解）
```

#### 6-2. 因果推論レポート（Causal Analysis Report）
```markdown
## 因果分析：[施策名] の増分効果

### 1. 問い（Estimand）
「2026年6月にIndeedを追加したことで、応募数は何件増えたか」（ATT: 処置群における平均処置効果）

### 2. 手法と選定理由
- 採用手法：Synthetic Control（対照候補：他6社の同期間応募数）
- 選定理由：A/Bテスト不可（媒体は同時に1構成しか出せない）、対照群が単独では存在しないため合成対照で反実仮想を構築

### 3. 識別の前提と検証
| 前提 | 検証方法 | 結果 |
|---|---|---|
| 平行トレンド | 施策前6ヶ月のトレンド一致（図1） | RMSPE 0.42、目視でも一致 ✅ |
| 交絡なし | 同期間の競合出稿・季節性・媒体アルゴ変更を確認 | 6月はGWなし・競合動きなし ✅ |
| 波及なし（SUTVA） | 対照6社がIndeed追加の影響を受けていないか | 商圏重複なし ✅ |

### 4. 推定結果
- 点推定：応募 **+3.2件/月**
- 95%信用区間：**+1.4 〜 +5.0件**
- Placebo test：対照6社に同じ手法を適用 → 6社中5社で効果なし（p ≈ 0.17）
- 増分CPA：¥9,900（既存平均CPA ¥12,100 より18%安い）

### 5. 反証チェック（Refutation）
- [x] 施策前の偽の施策日でDiDを実行 → 効果なし（期待通り）
- [x] 対照群を入れ替えて再推定 → 符号・オーダーが一致
- [x] 逆の結論を支持するデータを探索 → 6月の自然流入増加が要因である可能性は残る（自然検索セッション+6%）

### 6. 結論と因果の階段レベル
```

### Step 8: 失敗パターン & 回避策

> Daily Knowledge Log に蓄積済みの失敗（軸のゼロ基線、営業日補正、外れ値、多重比較、CPA定義、2軸グラフ、SRM）は**既に対策済み**。ここでは**スキル強化に伴って新たに発生する失敗**を扱う。

#### 失敗1: 高度な手法を使うこと自体が目的化し、意思決定に繋がらない（Method Theater）
- **どう起きるか**：Synthetic Control やベイズ階層モデルを実装したのが嬉しくて、Ryota や経営者に手法の説明から始めてしまう。読み手は「難しい」で読むのをやめ、結局「で、どうすれば？」に戻る。分析工数は3倍、意思決定は0。
- **兆候**：レポートの1ページ目に手法名が出てくる／「事後分布」「傾向スコア」がサマリーに登場する／読み手から質問が来ない（＝読まれていない）。
- **回避策**：
  1. **DAR（F1）を着手前に埋める**。Decision が書けない分析は高度な手法を使う資格がない。
  2. **手法は付録に隔離**。Executive Summary（6-1）に統計用語を1語も入れない。「Bが勝つ確率89%」は可、「事後分布のHDI」は不可。
  3. 手法選定は「**最も単純で結論が変わらない方法**」を選ぶ。単純な前後比較と Synthetic Control で結論が同じなら、前後比較で報告し Synthetic Control は検証済みの脚注にする。

#### 失敗2: 因果推論の識別仮定を検証せず、「因果を測った」と誤って断言する
- **どう起きるか**：DiD や Synthetic Control は**平行トレンド・交絡なし・波及なし（SUTVA）**が成り立って初めて因果になる。ライブラリは仮定を検証せず数値を返すため、仮定が壊れていても綺麗な信用区間が出てしまう。Lv1（相関）の結果に Lv2（介入）の看板を付けて出すのは、単なる相関誤報告（2026-07-01参照）より**説得力がある分だけ有害**。
- **兆候**：平行トレンドの図を描いていない／Placebo test をしていない／「たまたま他の施策も同時期に始まっていた」を確認していない。
- **回避策**：
  1. **因果レポート（6-2）の「3. 識別の前提と検証」を空欄で提出することを禁止**。検証できなければ Lv1 と明記して降格する。
  2. Placebo test（対照群に同手法を適用して効果が出ないことの確認）と、施策前の偽日付テストを**必須ゲート化**。
  3. DoWhy の refutation メソッドを機械的に通す（ランダム共変量追加・データ部分削除・処置のランダム化）。
  4. 同時期に走った他施策を Ryota に必ずヒアリングする（社内で把握していない営業活動・紹介経由がよくある）。

#### 失敗3: ベイズの事前分布を無自覚に設定し、結論を事前分布で作ってしまう
- **どう起きるか**：小サンプルではデータより事前分布の影響が大きい。「過去実績ベースの事前分布」を強く置くと、新施策の効果が事前分布に引き戻されて（shrinkage）「効果なし」になる。逆に希望的な事前分布を置けば「効果あり」も作れる。**恣意的に結論を選べる状態**は、頻度論のp-hacking より批判しづらい分だけ危険。
- **兆候**：事前分布の設定根拠がレポートに書かれていない／感度分析をしていない／事前分布を変えたら結論が変わることを知らない。
- **回避策**：
  1. **事前分布は必ずレポートに明記**（分布・パラメータ・設定根拠）。
  2. **感度分析を必須化**：無情報 / 過去実績ベース / 保守的 の3種で再計算し、**結論が変わるかを併記**。結論が変わる場合は「データが足りず判断保留」と正直に書く。
  3. 事前分布は**分析結果を見る前に決めて記録**する（事前登録）。結果を見てから事前分布を選ぶのは禁止。
  4. 階層ベイズの pooling は、クライアント間の異質性（業種・商圏・規模）が大きすぎる場合は使わない。7社を無条件に同質と扱わない。

#### 失敗4: データ基盤の自動化を進めた結果、誰も数値を疑わなくなる（Automation Blindness）
- **どう起きるか**：dbt でパイプラインを組み Looker Studio が毎朝自動更新されるようになると、「システムが出した数字」として無批判に信頼される。媒体側の管理画面仕様変更やタグの二重発火（Deng 2026-07-01参照）でパイプラインが静かに壊れても、グラフは何事もなく描画され続ける。**手作業時代は目視で気づけた異常が、自動化で見えなくなる**。
- **兆候**：ダッシュボードを開いても誰も驚かない／データ品質テストが未整備／「先月から同じ数字が出ている」ことに気づかない。
- **回避策**：
  1. **Great Expectations / dbt test を先に作ってから自動化する**（応募数が負・CVR>100%・前月比±80%超・7日連続同値・レコード数0 を検知）。
  2. **異常検知アラート**（本ファイル既存の INFO/WARNING/CRITICAL 体系）をパイプラインに接続し、CRITICAL は Slack で即時通知。
  3. **月1回の目視監査**：自動値と管理画面の実数を1社ずつ突合（ローテーションで7社を7ヶ月で1周）。
  4. **サイレント失敗の禁止**：データ取得0件はエラーとして落とす。「0件を正常として通す」設計にしない。

#### 失敗5: 可視化を洗練させすぎて、クライアントの現場が触れなくなる
- **どう起きるか**：Streamlit や Looker Studio で高機能なダッシュボードを作ると、フィルタ・タブ・ドリルダウンが増える。しかしクライアント（建設業の経営者・採用担当）は月1回しか開かず、操作を前提にした設計は成立しない（2026-08-16参照）。結果、Ryota に「見方が分からない」と問い合わせが飛び、Ryota の工数が増えて Shun の評価が下がる。
- **兆候**：ダッシュボードのタブが3つ以上／フィルタが4つ以上／「使い方の説明」が必要／閲覧ログが月1回未満のクライアントがある。
- **回避策**：
  1. **クライアント向けは1画面・スクロールのみ・フィルタ0〜1個**。深掘り用は社内向けに分離する。
  2. **期間・集計基準・確定状態をタイトルに焼き込む**（「2026年7月1日〜7月31日／JST／確定値」）。
  3. **PDF/画像でも成立するか**を必ず確認（経営者は印刷して会議に持ち込む）。
  4. リリース後1ヶ月の**閲覧ログを確認**し、開かれていないダッシュボードは廃止して静的レポートに戻す。作り込みの継続は使われていることが条件。
